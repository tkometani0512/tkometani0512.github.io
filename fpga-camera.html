Real-Time FPGA Camera-to-VGA Video Pipeline

Processorless OV7670 video capture and display on a Nexys A7-100T FPGA

A course project (CPE 487, Spring 2026, Prof. Byett) that configures an OV7670 camera over SCCB/I2C, reconstructs its pixel stream into 12-bit RGB, buffers complete frames in dual-port Block RAM, and renders a scaled, centered VGA output — with capture, buffering, scaling, and display running entirely in FPGA logic, no processor in the data path.

Overview

This project captures live 320×240 video from an OV7670 camera and displays it on a standard VGA monitor using a Nexys A7-100T FPGA. The camera feed is captured in real time over an 8-bit parallel bus, stored in a dual-port Block RAM frame buffer, and displayed centered within an 800×600 VGA signal — doubled 2×2 to fill a 640×480 area with black borders on all sides. The entire pipeline runs in programmable logic; there is no soft-core or embedded processor involved in capture, buffering, scaling, or display.

Two hardware switches provide runtime control: SW0 freezes the current frame indefinitely, and SW1 applies a real-time color-invert (negative) filter.

System architecture

Five modules make up the pipeline: a clock wizard generating two independent clocks, an SCCB/I2C configuration master, a three-state capture FSM, a dual-port Block RAM frame buffer, and a VGA sync generator. camera_top.vhd instantiates and wires all of them together, and additionally hosts the BRAM-latency compensation logic, the 2×2 pixel scaling/centering math, and the freeze/invert controls.

Capture FSM

The OV7670 sends each pixel over two byte cycles on an 8-bit bus, so ov7670_capture.vhd runs a three-state Moore FSM to track camera timing and reassemble pixels:

  • WAIT_VSYNC — idles until a VSYNC pulse marks the start of a new frame, then resets row/column counters.
  • WAIT_HREF — waits for HREF to go high, marking the start of an active row.
  • CAPTURE — reads one byte per PCLK pulse while HREF is high; the first byte is latched, and the second byte is combined with it to form a complete 12-bit RGB pixel, which is written to the frame buffer at the calculated address.
ov7670_capture.vhd — state machine core 
CASE state IS
    WHEN WAIT_VSYNC =>
        IF vsync = '1' THEN
            row <= (OTHERS => '0');
            col <= (OTHERS => '0');
            state <= WAIT_HREF;
        END IF;

    WHEN WAIT_HREF =>
        IF row >= 240 THEN
            state <= WAIT_VSYNC;
        ELSIF href = '1' THEN
            col <= (OTHERS => '0');
            state <= CAPTURE;
        END IF;

    WHEN CAPTURE =>
        IF href = '0' THEN
            row <= row + 1;
            state <= WAIT_HREF;
        ELSE
            IF byte_sel = '0' THEN
                hi_byte <= d;          -- first byte cycle
                byte_sel <= '1';
            ELSE
                dout <= d(3 DOWNTO 0) & hi_byte(3 DOWNTO 0) & d(7 DOWNTO 4);
                -- second byte cycle: combine into a 12-bit RGB pixel
                ...
            END IF;
        END IF;
END CASE;

Clock domains

The camera capture path and the VGA display path run on independent clocks generated by a modified clock wizard: an approximately 24 MHz clock drives the camera's XCLK input and the capture FSM, while a separate ~40 MHz clock drives VGA timing and the display-side read logic. Because these two clock domains have no fixed phase relationship, the frame buffer had to be a true dual-port memory that could be written and read independently — one port clocked by the camera's pixel clock, the other by the VGA pixel clock — rather than a single-clock buffer with arbitration logic.

Frame-buffer architecture

frame_buffer.vhd is a dual-port Block RAM sized for a full QVGA frame: 320 × 240 = 76,800 locations, each storing a 12-bit RGB pixel (4 bits red, 4 green, 4 blue). Port A is the write port, driven by ov7670_capture on the camera pixel clock; Port B is the read port, driven by the VGA sync logic on the 40 MHz display clock. The two ports operate independently with no shared arbitration.

Pixel-address calculation

The write-side address for each captured pixel is calculated directly from the current row and column counters:

addr = row × 320 + col   // 17-bit address, 320×240 = 76,800 locations

On the read side, the same addressing scheme is applied in reverse to map from display coordinates back to camera-frame coordinates (see the scaling section below).

Scaling and centering

The lab's test monitor did not support 640×480 @ 60/72 Hz reliably, so the design targets 800×600 @ 60 Hz instead. The captured 320×240 image is scaled 2× in each dimension to 640×480, then centered inside the 800×600 frame with an 80px border on the left/right and a 60px border on the top/bottom.

camera_top.vhd — read-side scaling and centering 
IF col >= 80 AND col < 720 AND
   row >= 60 AND row < 540 THEN
    cam_col := (col - 80) / 2;
    cam_row := (row - 60) / 2;
    addr := cam_row * 320 + cam_col;
    fb_addr_b <= STD_LOGIC_VECTOR(to_unsigned(addr, 17));
    in_frame <= '1';
ELSE
    fb_addr_b <= (OTHERS => '0');
    in_frame <= '0';   -- outside the image area: display black
END IF;

Dividing the display coordinate by 2 after subtracting the border offset maps every 2×2 block of VGA output pixels back to a single source pixel, and in_frame gates the color output to black whenever the current display position falls outside the centered image area.

BRAM-latency debugging

Synchronous Block RAM returns read data one clock cycle after the address is presented. Left uncompensated, this delay misaligned the image by a pixel relative to the border logic — the in_frame gate and the returned pixel data were one cycle out of sync, corrupting the edges of the displayed image. The fix was to register the address calculation and the in_frame signal together in the same clocked process, so that both the gating decision and the corresponding BRAM output arrive at the display logic on the same cycle.

SCCB / I2C camera configuration

The OV7670 needs a startup register sequence over its SCCB bus (I2C-compatible) before it will output a usable video signal. i2c_config.vhd drives this sequence at startup: a 25 kHz SCCB clock, a 40 ms power-on delay before the first transmission, a 50 ms pause after the software-reset register, and open-drain behavior on the SIOD data line implemented with tri-state logic. Approximately 60 registers are configured, including the color-format registers (COM7/COM15) that select RGB444 output. The register set is sourced from Mike Field's published OV7670 configuration, with modifications for this project's color-mode setting.

Hardware controls

SW0 — Freeze frame

camera_top.vhd — freeze-frame write-enable gating 
capture_we <= fb_we_a and not sw_freeze;
-- when frozen, capture_we is forced to '0' so the BRAM
-- stops being written; the VGA read port keeps running
-- normally, displaying the last captured frame.

SW1 — Color invert

camera_top.vhd — invert filter 
pixel_out <= fb_dout XOR (sw_invert & sw_invert & sw_invert & sw_invert &
                          sw_invert & sw_invert & sw_invert & sw_invert &
                          sw_invert & sw_invert & sw_invert & sw_invert);
-- replicates the single switch bit across all 12 pixel bits;
-- XOR with 0 leaves the pixel unchanged, XOR with 1 flips
-- every bit, producing a real-time color-negative effect.

  • Startup SCCB/I2C camera configuration completes correctly

Remaining improvements

Open engineering issue: color calibration

Pixel byte ordering and color-channel mapping still produce visible color errors — the OV7670 outputs RGB444 data in GRB byte order rather than the expected RGB order, and some camera modules may be missing pull-up resistors on the SIOC/SIOD lines, which is a suspected contributor to the remaining blue-channel inaccuracy. The video pipeline, motion response, frame buffering, freeze frame, and invert filter all function correctly; full color accuracy remains an area for continued debugging rather than a claim this project makes.

Next steps identified for this design: re-verify the GRB-to-RGB byte remapping against the datasheet, confirm whether external pull-ups are needed on SIOC/SIOD for reliable SCCB communication on this camera module, and re-test color accuracy under controlled lighting.
